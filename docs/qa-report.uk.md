# QA-звіт — Virtual Data Room

**Версія:** коміт `9c85149`, живий сайт · **Протестовано:** 2026-10-20 · **Час:** 24 години

## Висновок: ❌ Ще не готовий для реального клієнта, але близько

**Більшість працює добре:**
- другий користувач справді нічого не може змінити;
- через публічне посилання не можна дістатися до інших папок;
- відкликання доступу працює одразу;
- папки та файли поводяться так, як сказано у вимогах.

**Один баг блокує реліз:**

| Блокер | Чому |
|---|---|
| **F-21:** будь-хто може забрати доступ, призначений комусь іншому | Власник ділиться папкою з email, для якого ще немає акаунта. Це нормально, коли запрошуєш юриста покупця. Хто першим зареєструється з цим email, той отримає документи, бо застосунок ніколи не перевіряє, що людина володіє цим email. Я підтвердив це на живому сайті. |

**Можна випускати, коли:**
1. Виправлено F-21: підтверджувати email при реєстрації або надсилати на цей email посилання-запрошення.
2. Бажано також F-02 і F-10 (середні):
   - сервер має перевіряти, що завантажений файл — справжній PDF заявленого розміру;
   - в одного елемента має бути тільки одне публічне посилання, щоб відкликання доступу закривало все.

Це дні роботи, а не тижні. Для кожного виправлення вже є автотест, який його підтвердить.

## Головні проблеми та ризики
**21 баг:** 1 з високим, 4 із середнім і 16 з низьким пріоритетом. Є також 3 ризики в дизайні.

У них кілька спільних причин:
1. **Немає перевірки особи** (F-21). Реєстрація не підтверджує email, а надання доступу довіряє email.
2. **Сервер довіряє клієнту** (F-02, F-04, F-13):
   - він приймає тип і розмір файлу, які назвав клієнт;
   - він приймає будь-яке розширення через API;
   - він ігнорує невідомі поля.
3. **Дублі, коли два запити приходять одночасно** (F-01, F-10, F-11). У базі даних немає правила, що імена або посилання мають бути унікальними, тому перевірка не спрацьовує під навантаженням. Одне виправлення (правила унікальності в базі даних) закриває всі три.
4. **Імена не очищуються** (F-03): дозволені невидимі символи та символи, що міняють напрямок тексту.
5. **Сесія** (F-15, R-03, R-04):
   - токен живе 7 днів, і його не можна скасувати;
   - інші вкладки показують дані після виходу;
   - немає ліміту на спроби логіну.

## Автотести

**65 автотестів, повний запуск займає приблизно 3 хвилини:**
- 50 перевіряють те, що працює, і вони проходять;
- 15 відтворюють відомі баги: вони навмисно падають, і кожен падає з правильної причини.

| Рівень | Тести | Що покриває |
|---|---|---|
| Контракт | 3 + кожна відповідь API | Жива документація API збігається зі збереженою копією, а кожна відповідь API в кожному тесті збігається з документацією |
| API | 56 | Smoke-перевірка, логін, папки, файли, правила доступу, публічні посилання, 14 відомих багів |
| Браузер | 6 | Завантаження і перегляд, публічне посилання → відвідувач → відкликання доступу, другий користувач бачить тільки читання, логін, F-10 |

**Не автоматизовано:**
- **F-21:** тест мав би при кожному запуску створювати нові акаунти на спільному продакшні;
- **drag and drop:** те саме завантаження тестується через вибір файлу у вікні;
- **доступ до всієї кімнати даних:** на спільному демо-акаунті другий користувач отримав би доступ до чужих даних;
- **F-15 і F-16.**

**Про фреймворк:**
- він безпечний для спільного сайту: своя папка на кожен запуск, наприкінці видаляється;
- паролі беруться тільки з `.env` або CI secrets;
- власний звіт показує статус кожного відомого бага;
- GitHub Actions запускає його на кожен push і щоночі.

## Що тестувати або автоматизувати далі
1. **Після виправлень:** тести відомих багів — це приймальні тести. Коли вони проходять, прибрати «очікувано падає». Додати автотест для F-21 в окремому тестовому середовищі.
2. **Для розробників:** сьогодні в продукті є 42 unit-тести, які не використовують справжню базу даних, немає frontend-тестів і немає CI. Далі додати:
   - тести зі справжньою базою даних (унікальні імена, видалення, надання доступу);
   - тести перевірки вхідних даних;
   - простий CI.
3. **Безпека, в окремому середовищі:**
   - ліміти спроб логіну;
   - налаштування сховища (ліміти розміру і типу);
   - заголовки безпеки (security headers).
4. **Великі дані:** продукт заявляє, що в одній кімнаті даних може бути 100 000 файлів. Перевірити швидкість списку, швидкість видалення і дуже глибокі папки.
5. **Більше браузерних тестів:**
   - справжній drag and drop;
   - повторне завантаження після помилки;
   - діалог переміщення;
   - екран телефона;
   - Firefox і Safari.
6. **Більше вручну:**
   - після виходу наступний користувач не повинен бачити дані попереднього (у README продукту сказано, що це виправлено);
   - відкриття посилання без логіну;
   - що буде, коли спливе термін дії 7-денного токена.
