## 1. Мета
Дізнатися, чи можна віддати цей продукт реальному клієнту для корпоративної угоди.

У кімнаті даних (data room) головне завдання одне: документи бачать тільки потрібні люди, а власник може забрати доступ. Тому більшість часу я витратив на надання доступу та правила доступу, а на решту — менше.

## 2. Що я тестую, а що ні

**Я тестую** усе із `task.md`:
- логін і реєстрацію;
- папки: створення, вкладеність, перейменування, видалення з попередженням, breadcrumbs (шлях угорі сторінки);
- файли: завантаження кількох одразу, перегляд, перейменування, переміщення, видалення;
- надання доступу: уся кімната, папка або один файл, через публічне посилання або конкретній людині, і відкликання доступу.

**Я також тестую:**
- помилки та порожні стани;
- API;
- базову безпеку: чи може хтось відкрити чуже;
- що буде, коли дві дії відбуваються в один момент.

**Я не тестую, і чому:**
- **Навантаження і стрес:** сайт — це спільний продакшн, яким саме зараз користуються інші кандидати.
- **Справжній злам:** брутфорс та атаки поза межами завдання; я перевіряю тільки правила.
- **Багато браузерів:** тільки Chrome.
- **Доступність (accessibility):** на неї немає часу за 24 години.

## 3. Як я тестую
1. **Спочатку я читаю код і документацію API** (приблизно 1 година). Продукт з відкритим кодом, тому я виписав усі 33 операції API (28 адрес), правила доступу та наявні тести. Це дало мені список місць, де щось *може* бути зламано. Ніщо не потрапляє у звіт про баги, поки я не відтворю це на живому сайті.
2. **Потім я тестую вручну, область за областю** (список нижче). Власник і другий користувач залогінені одночасно у двох браузерах, тому я бачу, що бачить інша людина.
3. **Для кожного бага я перевіряю, як на нього натрапить реальний користувач.** Деякі баги трапляються тільки через API або тільки після оновлення сторінки. Тоді я ставлю їм нижчий пріоритет. Наприклад, F-10 опустився з високого до середнього, коли я спробував звичайний подвійний клік руками.
4. **Я автоматизую найважливіші перевірки**, плюс тест на кожен підтверджений баг, який можна безпечно автоматизувати на спільному сайті.

## 4. Зони ризику
Для кожної зони я оцінюю дві речі:
- **Імовірність:** наскільки ймовірно, що там є баги (залежить від складності та від того, що я бачив у коді);
- **Вплив:** наскільки поганим буде баг там для клієнта.

Чим більше обох, тим раніше я тестую зону. Серйозність (severity) — це інше: її я ставлю пізніше, для кожного знайденого бага.

## 6. План автоматизації (піраміда тестів)

```
          /\        Браузерні тести (мало)   - тільки те, що потребує справжнього UI
         /  \       завантаження → перегляд, публічне посилання → відкликання, перегляд тільки для читання, логін
        /----\
       / API  \     API-тести (більшість)    - усі правила: папки, файли, доступ,
      / тести  \                               посилання, + тести на підтверджені баги
     /----------\
    /  контракт  \   кожна відповідь API порівнюється з офіційним описом API
   /--------------\
  /   unit-тести   \  частина коду продукту - робота розробників
 /------------------\ (я переглянув їхні 42 тести і виписав, чого бракує)
```

- **Більшість тестів — це API-тести.** Усі правила доступу живуть в API, а API-тести швидкі й стабільні.
- **Браузерних тестів мало:** тільки те, що видно лише в UI, наприклад приховані кнопки і сторінку після відкликання доступу.
- **Відомі баги стають тестами, де це можливо.** Такий тест описує *правильну* поведінку і позначений як «очікувано падає». Коли розробники виправлять баг, тест про це повідомить.
- **Безпечно для спільного сайту.** Кожен запуск створює свою папку і наприкінці її видаляє. Він ніколи не чіпає чужі дані.

## 7. Коли починати і коли тестування закінчене
**Початок:** сайт і API працюють, а тестові акаунти можуть залогінитися.

**Закінчено, коли:**
- усі сесії пройдено;
- кожен баг має серйозність і пріоритет;
- автотести проходять (відомі баги падають, як і очікувано);
- у QA-звіті сказано, чи готовий продукт.

## 8. Серйозність і пріоритет
- **Серйозність:**
  - Критична: витік або втрата даних без обхідного шляху;
  - Висока: порушена основна вимога або слабке місце в безпеці;
  - Середня: працює частково, або є обхідний шлях;
  - Низька: косметична або дрібна.
- **Пріоритет:** Високий = виправити до релізу, Середній = у наступній ітерації, Низький = у беклог.
