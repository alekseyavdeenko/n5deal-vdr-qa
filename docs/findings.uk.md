**Як читати шкали:**
- **Серйозність** — наскільки великої шкоди завдає баг: критична, висока, середня, низька.
- **Пріоритет** — як швидко це треба виправити: високий = до релізу, середній = у наступній ітерації, низький = у беклог.
- **«Як відтворити»** дає короткі кроки для кожного бага і показує, чи може звичайний користувач натрапити на нього в UI, чи тільки той, хто звертається до API напряму. Я перевірив це для кожного бага, і через це змінилися кілька пріоритетів.
- Колонка **Автотест**: ✅ означає, що для бага є автотест (API або браузерний); «немає» — що його перевірено тільки руками.

## Підсумок

21 баг:
- 1 з високим пріоритетом;
- 4 із середнім пріоритетом;
- 16 з низьким пріоритетом.

Також є 3 ризики в дизайні.

**Найважливіше (F-21):** якщо власник ділиться папкою з email, для якого ще немає акаунта, то папку отримає той, хто першим зареєструється з цим email. Застосунок не перевіряє, що людина справді володіє цим email. Я підтвердив це повним сценарієм на живому сайті.

## Що працює добре
Усе це я перевірив, і більшість покрито автотестами.
- **Другий користувач нічого не може змінити.** Усі 12 способів змінити дані повертають 404. Також він не може відкрити інші папки й файли власника, якщо підмінити id в адресі (IDOR — доступ до чужих даних через підміну id).
- **Публічне посилання показує тільки те, чим поділилися.** Через нього не можна дістатися до батьківської папки, сусідніх папок чи інших файлів.
- **Відкликання доступу працює одразу.** Посилання показує "This link has been revoked". Якщо другий користувач тримає папку відкритою, його наступний клік показує "you don't have access".
- **Папки:**
  - дублікати назв заблоковані, незалежно від великих літер і пробілів;
  - ліміт 200 символів працює;
  - breadcrumbs (шлях угорі) правильні;
  - попередження про видалення показує, скільки папок і файлів буде видалено.
- **Файли:**
  - конфлікти назв отримують "(1)", "(2)" при завантаженні, перейменуванні й переміщенні;
  - перегляд і скачування працюють;
  - скачаний файл має правильну назву.
- **Завантаження:** файли неправильного типу й файли понад 50 MB відхиляються із зрозумілим повідомленням.
- **Базова безпека:**
  - HTML у назвах показується як текст, а не виконується;
  - вхід дає однакове повідомлення і для неправильного пароля, і для невідомого email.

## Деталі високих і середніх багів

### F-21 — Будь-хто може забрати доступ, призначений незареєстрованому email
![F-21](evidence/F-21-squatter-receives-share-right-after-signup.jpg)

**Кроки:**
1. Власник ділиться папкою "Confidential - Financials 2026" з `cfo.n5qa6468@example.com`. Акаунта для цього email ще немає, і застосунок дозволяє поділитися.
2. Хтось інший відкриває Sign up і реєструється саме з цим email і будь-яким паролем.
3. Він відкриває "Shared with me".

**Очікувано:** доступ отримує тільки справжній власник email. Наприклад, реєстрація спочатку просить підтвердити email, або поділитися з невідомим email не можна.

**Фактично:** акаунт працює одразу, без підтвердження email. Конфіденційна папка вже лежить у "Shared with me" і відкривається.

**Чому це важливо:** в угоді нормально запрошувати людей, які ще не мають акаунта, наприклад юристів чи аудиторів покупця. Той, хто знає або вгадає їхню робочу пошту, може отримати документи першим.

### F-02 — Завантажені файли не перевіряються на сервері
![F-02](evidence/F-02-F-18-fake-pdf-in-viewer-uuid-title.jpg)

**Кроки:** перейменувати будь-який не-PDF файл на `something.pdf` і завантажити його.

**Очікувано:** сервер перевіряє, що файл справді є PDF (починається з `%PDF-`), і перевіряє його справжній розмір.

**Фактично:**
- Файл зберігається і показується як PDF. Другий користувач бачить "Failed to load PDF document".
- Через API можна написати, що «файл має 10 байт», а потім завантажити більший. Він зберігається зі справжнім розміром, тож ліміт 50 MB нічого не захищає.

**Чому це важливо:**
- У data room мають лежати тільки справжні документи.
- Оскільки зареєструватися може будь-хто (див. F-21), будь-хто також може забити сховище великими файлами.

### F-10 — Два публічні посилання на одну папку; Revoke закриває тільки одне
![F-10](evidence/F-10-share-dialog-shows-one-of-six-active-links.jpg)

**Кроки:** надіслати два запити "create public link" для тієї самої папки в один момент (автоматичний подвійний клік або скрипт). Потім натиснути "Revoke public link" у вікні Share.

**Очікувано:** одне посилання на папку. Після Revoke жодне посилання не працює.

**Фактично:**
- Створюється 2 посилання. Вікно показує одне з них.
- Після Revoke воно тихо показує друге посилання, яке досі відкриває папку.
- Із 6 запитів в один момент: 6 посилань, і 5 з них досі працюють після Revoke.

**Наскільки це ймовірно:** я швидко натиснув кнопку двічі руками, і UI заблокував другий клік. Тож звичайний користувач рідко на це натрапить. Але це все одно важливо: коли таке стається, власник думає, що доступ закрито, а він не закритий.

**Ідея виправлення:** дозволити в базі тільки одне активне посилання на елемент і зробити так, щоб Revoke закривав усі.

### F-01 — Файли з однаковою назвою в одному завантаженні не перейменовуються
![F-01](evidence/F-01-F-06-F-08-duplicate-names-empty-file-error-local-dates.jpg)

**Кроки:** в одному завантаженні вибрати два файли `report.pdf` з різних папок (або перетягнути їх разом).

**Очікувано:** другий стає `report (1).pdf`, так само як коли завантажувати їх по одному.

**Фактично:** обидва зберігаються як `report.pdf`, і відрізнити їх неможливо.

### F-03 — Невидимі символи й символи, що перевертають напрямок тексту, в назвах
![F-03](evidence/F-03-spoofed-names-and-duplicates.jpg)

**Кроки:** створити папки або файли з такими назвами:
- `invoice` + символ напрямку справа наліво (U+202E) + `fdp.exe`
- `case-1` + невидимий пробіл нульової ширини
- назви з табуляцією або розривом рядка

**Очікувано:** ці символи відхиляються або видаляються.

**Фактично:**
- усі вони приймаються;
- перша назва показується як "invoiceexe.pdf", хоча насправді закінчується на ".exe";
- дві папки `case-1` виглядають однаково.

## Докази через API для багів, яких не видно в UI
Це справжні запити й відповіді живого API за 2026-10-20. Id скорочено.

**F-11 — 10 створень однієї папки в один момент:**
```
POST /folders {"name":"race-dup", ...}  x10 одночасно
→ 201, 201, 201, 201, 201, 201, 201, 201, 201, 201   (10 папок "race-dup")
```

**F-12 — завантаження, яке так і не завершилось, тримає назву:**
```
POST /files/upload-intent {"name":"ghost.pdf", ...}   → 201 {"name":"ghost.pdf"}       (файл так і не завантажили)
POST /files/upload-intent {"name":"ghost.pdf", ...}   → 201 {"name":"ghost (1).pdf"}
GET  /folders/{id}/contents                           → {"items":[]}                  (папка виглядає порожньою)
```

**F-13 — одруківка в назві поля переносить файл у корінь кімнати:**
```
PATCH /files/{id}/move {"targetFolderID":"<id папки>"}   (правильно: targetFolderId)
→ 200 {"folderId": null, ...}
```

**F-14 — помилки сервера замість нормальних помилок:**
```
POST   /folders {"name":"nul\u0000name", ...}       → 500 {"message":"Internal server error"}
DELETE /files/{id}  x3 в один момент                → 204, 500, 500
POST   /files/{id}/complete  (нічого не завантажено) → 500 {"message":"Could not verify the upload"}
```

**F-17 — текст помилки показує, чи існує елемент** (від імені другого користувача):
```
GET /folders/{папка власника}/contents   → 404 {"message":"Resource not found"}
GET /folders/{випадковий id}/contents    → 404 {"message":"Folder not found"}
```

**F-04 — API дозволяє інше розширення:**
```
PATCH /files/{id} {"name":"report.exe"}   → 200 {"name":"report.exe", "mimeType":"application/pdf"}
```

**F-07 — інформація про публічне посилання показує внутрішній id кімнати будь-кому:**
```
GET /public/{token}   (без входу)
→ 200 {"resourceType":"FOLDER","resourceName":"share-root","dataRoomId":"05f75e29-…", ...}
```
