## 1. Як я тестував
1. **Я почав з коду.** Продукт з відкритим кодом, тому за першу годину я прочитав документацію API (33 операції API на 28 адресах), правила доступу в коді та наявні тести. Так я отримав список місць, де щось може бути зламано. Місце потрапляло у звіт про баги тільки після того, як я відтворив проблему на живому сайті.
2. **Я тестував вручну, область за областю:**
   - імена та папки;
   - завантаження;
   - публічні посилання;
   - другий користувач;
   - дві дії в один момент;
   - інтерфейс.

   Власник і другий користувач були залогінені одночасно у двох браузерах, тому я міг відкликати доступ, поки інша людина дивилася на папку.
3. **Я перевіряв, як реальний користувач натрапить на кожен баг.** Деякі баги трапляються тільки через API або після оновлення сторінки. Таким я ставив нижчий пріоритет. Наприклад, баг «два публічні посилання» (F-10) спочатку виглядав дуже серйозним, але звичайний подвійний клік руками блокується інтерфейсом, тому він опустився до середнього.
4. **Я автоматизував найважливіші перевірки.** 14 з 28 багів також отримали свій тест: усі 5 багів середнього пріоритету і 9 низького. F-21 з високим пріоритетом не можна автоматизувати на спільному сайті (кожен запуск створював би новий акаунт); решту низьких перевірено руками. Див. колонку «Автотест» у звіті про баги.

Сайт — це спільний продакшн, яким користуються й інші кандидати. Тому я не робив навантажувального тестування і ніколи не змінював чужі дані. Мої тестові дані лежали в моїх власних папках, і наприкінці я їх видалив. Дві речі прибрати не вдалося, бо продукт не вміє їх видаляти: додатковий акаунт, який я зареєстрував, щоб довести F-21 (`cfo.n5qa6468@example.com`, ім'я "Hacker"), і дві додаткові кімнати цього акаунта з перевірки F-25. Доступ до цілої кімнати, використаний у TC-105, я відкликав одразу після перевірки.

## 2. Автотести

**Інструменти:** Playwright + TypeScript і для API-тестів, і для браузерних тестів, плюс Ajv, щоб порівнювати відповіді API з документацією API.

```
          /\        Браузер (8)     завантаження → перегляд, публічне посилання → відкликання,
         /  \                       перегляд тільки для читання, логін, F-10, F-22, F-28
        /----\
       / API  \     API (57)        smoke, логін, папки, файли, правила доступу,
      / тести  \                    публічні посилання, 15 відомих багів
     /----------\
    /  контракт  \  (3 + кожна відповідь)  кожна відповідь API порівнюється з документацією API
   /--------------\
  /   unit-тести   \  частина продукту; я переглянув 42 тести розробників
 /------------------\
```

**Головні ідеї:**
- **Більшість тестів — це API-тести.** Усі правила доступу живуть в API, а API-тести швидкі й стабільні. Браузерні тести перевіряють тільки те, що видно лише в UI.
- **Кожна відповідь API перевіряється за документацією API.** Якщо API повертає щось, чого немає в документації, тест падає. Окремий тест попереджає, коли жива документація змінюється.
- **Безпечно на спільному сайті:**
  - кожен запуск створює свою папку `n5qa-<date>-<code>`;
  - кожен тест працює у своїй підпапці;
  - наприкінці все видаляється;
  - папки, які лишив запуск, що аварійно завершився, видаляються через 2 години.
- **Відомі баги — це теж тести.** Кожен тест описує *правильну* поведінку і позначений як «очікувано падає», тому запуск лишається зеленим. Коли виходить виправлення, Playwright повідомляє "expected to fail but passed" (очікувалося падіння, але тест пройшов). Невеликий власний звіт друкує, чому кожен відомий баг досі падає, наприклад `F-10: Expected 1 link, received 3`. Він пише «still reproduces» лише тоді, коли тест упав саме на перевірці бага; якщо тест зламався з іншої причини (підготовка даних, мережа), звіт пише «FAILED FOR ANOTHER REASON».
- **Жодних паролів у коді.** Їх читають з `.env` або з GitHub secrets. Тести, яким потрібен логін, пропускаються, якщо `.env` немає.

### Як запустити

```bash
npm ci
npm run install:browsers    # один раз: Chromium від Playwright
cp .env.example .env        # додати два тестові акаунти з README продукту
npm test                    # усе, приблизно 3 хвилини
npm run test:smoke          # швидка перевірка, що сайт працює
npm run test:api            # API-тести
npm run test:e2e            # браузерні тести
npm run test:e2e:headed     # браузерні тести, за якими можна стежити, сповільнені
npm run test:known-bugs     # статус кожного відомого бага
npm run report              # HTML-звіт
```

**Примітки:**
- Playwright 1.56 підтримує Node 18–24. Якщо у вас новіший Node (наприклад, 26), npm-скрипти самі запускають Playwright на Node 22 через `scripts/pw.mjs`, тож нічого не зависає. Node 22 npx завантажить один раз; у систему нічого не встановлюється. На Node 26 не запускайте `npx playwright` напряму: там зависають встановлення браузера, trace-файли і кінець прогону.
- Браузерні тести використовують Chromium від Playwright. `PW_CHANNEL=chrome` перемикає на встановлений Google Chrome.
- **CI** (`.github/workflows/qa.yml`) працює в три кроки: smoke + контракт → API → браузер. Він запускається на кожен push і щоночі. Тестові акаунти зберігаються як GitHub secrets.

**2. Те, що AI вважав багами, але це не баги**
- **«HTML-сторінка, завантажена як PDF, запуститься в браузері як сайт».** AI очікував цього з коду. На живому сайті сховище віддає такий файл як звичайний текст, тож небезпеки немає. У звіт це не потрапило.
- **«У панелі завантаження немає прогрес-бару, лише слово Uploading».** Це була перша швидка перевірка. Я подивився код і зробив скриншот під час завантаження файлу на 45 MB: у кожного файлу своя смужка прогресу. Вимогу виконано.

**3. Тести, які нічого не перевіряли**
- **«Обрив інтернету», якого не було.** Щоб перевірити кнопку Retry після обриву зв'язку, AI спершу імітував обрив неправильно: зламав одну функцію браузера, а застосунок шле запити через іншу (axios / XMLHttpRequest). Тобто обриву взагалі не було, і результат виглядав як «Retry працює». Я змусив перевірити, що обрив справді стався. З другої спроби він стався, і Retry виявився по-справжньому зламаним. Це баг F-22.
- **Тести «очікувано падає», які завжди зелені.** Тест на відомий баг позначений «очікувано падає». Він лишається зеленим щоразу, коли падає, з будь-якої причини, навіть через помилку в самому тесті. Тому я додав короткий звіт, який показує, чому саме падає кожен відомий баг, наприклад «Expected 1 link, received 3» (очікували 1 посилання, отримали 3). Звіт пише «still reproduces» лише тоді, коли тест упав саме на перевірці бага, а інакше — «FAILED FOR ANOTHER REASON». Так видно, що тест падає через баг, а не через щось інше.

**4. Неправильні цифри і вигадані деталі**
- **Підсумки на око.** AI написав «75 перевірок» у підсумку тест-кейсів, хоча їх було 68. Відтоді кожну цифру в документах рахує скрипт, а кожен ID автотесту в документах звіряється зі справжнім списком тестів.
- **Вигаданий id.** В одному прикладі запиту до API AI написав id, якого не було в жодній справжній відповіді. Я замінив його заглушкою. Кожен запит і відповідь у звіті мають бути справжніми.
- **«Кожна вимога має автотест».** Це була неправда: доступ до цілої кімнати не автоматизовано, бо на спільному демо-акаунті він показав би чужі дані. Речення виправили й додали причину.

**5. Лікування симптому замість причини**
- **Прогін тестів іноді не завершувався.** Перше «виправлення» AI (вимкнути trace-записи) лише сховало проблему, і зависання повернулося. Справжня причина — Node 26, якого Playwright ще не підтримує. Тепер npm-скрипти автоматично запускаються на Node 22, і прогін завершується сам.

**6. Що міг перевірити лише живий тестувальник**
- перетягнути справжній файл з Finder у браузер;
- справжній подвійний клік рукою (F-10);
- зареєструватися з чужим email із запрошення, щоб довести F-21.
