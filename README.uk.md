## Короткий результат
- **Висновок: ще не готовий.** Один баг блокує реліз.
- **Баг, що блокує (F-21):** якщо власник ділиться папкою з email, для якого ще немає акаунта, будь-хто може першим зареєструватися з цим email і отримати документи. Я підтвердив це на живому сайті.
- **Решта працює добре:**
  - другий користувач нічого не може змінити;
  - публічне посилання показує тільки те, чим поділилися;
  - відкликання доступу працює одразу.
- **Цифри:**
  - 28 багів: 1 з високим, 5 із середнім, 22 з низьким пріоритетом;
  - 85 перевірок у два раунди;
  - 68 автотестів.

## 1. Як я тестував
1. **Я почав з коду.** Продукт з відкритим кодом, тому за першу годину я прочитав документацію API (32 ендпоінти), правила доступу в коді та наявні тести. Так я отримав список місць, де щось може бути зламано. Місце потрапляло у звіт про баги тільки після того, як я відтворив проблему на живому сайті.
2. **Я тестував вручну, область за областю:**
   - імена та папки;
   - завантаження;
   - публічні посилання;
   - другий користувач;
   - дві дії в один момент;
   - інтерфейс.

   Власник і другий користувач були залогінені одночасно у двох браузерах, тому я міг відкликати доступ, поки інша людина дивилася на папку.
3. **Я перевіряв, як реальний користувач натрапить на кожен баг.** Деякі баги трапляються тільки через API або після оновлення сторінки. Таким я ставив нижчий пріоритет. Наприклад, баг «два публічні посилання» (F-10) спочатку виглядав дуже серйозним, але звичайний подвійний клік руками блокується інтерфейсом, тому він опустився до середнього.
4. **Я автоматизував найважливіші перевірки.** Кожен підтверджений баг теж отримав свій тест.

Сайт — це спільний продакшн, яким користуються й інші кандидати. Тому я не робив навантажувального тестування і ніколи не змінював чужі дані. Усі мої тестові дані лежали в моїх власних папках, які я видалив наприкінці.

## 2. Автотести

**Інструменти:** Playwright + TypeScript і для API-тестів, і для браузерних тестів, плюс Ajv, щоб порівнювати відповіді API з документацією API.

```
          /\        Браузер (8)     завантаження → перегляд, публічне посилання → відкликання,
         /  \                       перегляд тільки для читання, логін, F-10, F-22, F-28
        /----\
       / API  \     API (57)        smoke, логін, папки, файли, правила доступу,
      / тести  \                    публічні посилання, 15 відомих багів
     /----------\
    /  контракт  \  (3 + кожна відповідь)  кожна відповідь API порівнюється з документацією API
   /--------------\
  /   unit-тести   \  частина продукту; я переглянув 42 тести розробників
 /------------------\
```

**Головні ідеї:**
- **Більшість тестів — це API-тести.** Усі правила доступу живуть в API, а API-тести швидкі й стабільні. Браузерні тести перевіряють тільки те, що можна побачити лише в UI.
- **Кожна відповідь API перевіряється за документацією API.** Якщо API повертає щось, чого немає в документації, тест падає. Окремий тест попереджає, коли жива документація змінюється.
- **Безпечно на спільному сайті:**
  - кожен запуск створює свою папку `n5qa-<date>-<code>`;
  - кожен тест працює у своїй підпапці;
  - наприкінці все видаляється;
  - папки, які лишив запуск, що аварійно завершився, видаляються через 2 години.
- **Відомі баги — це теж тести.** Кожен тест описує *правильну* поведінку і позначений як «очікувано падає», тому запуск лишається зеленим. Коли виходить виправлення, Playwright повідомляє "expected to fail but passed" (очікувалося падіння, але тест пройшов). Невеликий власний звіт друкує, чому кожен відомий баг досі падає. Так видно, що він падає з правильної причини, наприклад `F-10: Expected 1 link, received 3`.
- **Жодних паролів у коді.** Їх читають з `.env` або з GitHub secrets. Тести, яким потрібен логін, пропускаються, якщо `.env` немає.

### Як запустити

```bash
npm ci
npm run install:browsers    # один раз: Chromium від Playwright
cp .env.example .env        # додати два тестові акаунти з README продукту
npm test                    # усе, приблизно 3 хвилини
npm run test:smoke          # швидка перевірка, що сайт працює
npm run test:api            # API-тести
npm run test:e2e            # браузерні тести
npm run test:e2e:headed     # браузерні тести, за якими можна стежити, сповільнені
npm run test:known-bugs     # статус кожного відомого бага
npm run report              # HTML-звіт
```

**Примітки:**
- Playwright 1.56 підтримує Node 18–24. Якщо в тебе новіший Node (наприклад, 26), npm-скрипти самі запускають Playwright на Node 22 через `scripts/pw.mjs`, тож нічого не зависає і нічого не треба встановлювати. На Node 26 не запускай `npx playwright` напряму: там зависають встановлення браузера, trace-файли і кінець прогону.
- Браузерні тести використовують Chromium від Playwright. `PW_CHANNEL=chrome` перемикає на встановлений Google Chrome.
- **CI** (`.github/workflows/qa.yml`) працює в три кроки: smoke + контракт → API → браузер. Він запускається на кожен push і щоночі. Тестові акаунти зберігаються як GitHub secrets.

## 3. Як я використовував AI

Я працював з Claude Code: Claude Opus як основний помічник, плюс помічники Claude Sonnet для окремих задач. Я користувався ним багато, свідомо, і перевіряв, що він зробив.

| Що | Що робив AI | Що робив я |
|---|---|---|
| Читання коду | Помічник прочитав код продукту і виписав API, правила доступу та 31 підозріле місце | Я сприймав це тільки як ідеї. Баг потрапляв у звіт тільки після того, як я відтворив його на живому сайті |
| Тестування | Надсилав API-запити і клікав по UI у двох браузерах одночасно | Я заходив у тестові акаунти (AI не має права вводити паролі), стежив за тестуванням і просив додаткові перевірки. Приклад: після виходу в одній вкладці я запитав «що буде після оновлення сторінки?», і це показало, що F-15 менший, ніж було записано спочатку |
| Повторна перевірка багів | Повторно тестував кожен баг так, як на нього натрапив би звичайний користувач | Я робив перевірки, де потрібна справжня людина: подвійний клік руками для F-10 і реєстрацію з чужим запрошеним email для F-21 |
| Документи | Писав чернетки | Я їх переглядав, просив простішу мову і сам ставив фінальні пріоритети |
| Автоматизація | Написав фреймворк і API-тести; помічник написав браузерні тести | Я запускав кожен тест на своєму комп'ютері, включно із запусками з видимим браузером, і повертав йому тести, що впали |

**Де AI помилявся і як я це помітив.** AI працював швидко й корисно, але регулярно помилявся. Моє правило: нічого не потрапляє у звіт чи тести, поки це не перевірено на живому сайті, скриптом або руками. Справжні приклади з цього завдання:

- **Баги, які виглядали гіршими, ніж є.** Перша чернетка перебільшувала кілька багів:
  - F-15 описував, що «інші вкладки показують дані після виходу». Я спитав, що буде після оновлення сторінки: наступний клік або оновлення ведуть на вхід, тож баг дрібний.
  - F-16 («Close веде в нікуди») трапляється лише після оновлення сторінки або коли файл відкрили за прямим посиланням.
  - F-11 (дублікати папок) не відтворюється через UI.
  - F-19 (довгі назви) на ноутбуці в порядку й ламається лише на телефоні.

  Усе це я перевірив так, як натрапив би справжній користувач, і знизив пріоритети.
- **«Серйозний» баг, який людина не відтворить.** Браузерний тест для F-10 створює два публічні посилання машинним подвійним кліком. Я двічі клікнув кнопку руками, і UI заблокував другий клік. Тому F-10 знизився з високого до середнього, а в описі тесту тепер сказано, що він відтворює гонку запитів, а не звичайний шлях користувача.
- **Баги, які не були багами.**
  - З коду AI припустив, що HTML-сторінка, завантажена як PDF, запуститься як веб-сторінка; на живому сайті сховище віддає її як звичайний текст.
  - Перша перевірка панелі завантаження показала «прогресу немає, лише слово Uploading»; код і скриншот показали справжню смужку прогресу.

  Жодне з цього не потрапило у звіт.
- **Тест, який нічого не перевіряв.** Щоб перевірити Retry після обриву мережі, AI спершу «зламав» `fetch`, але застосунок шле запити через axios (XMLHttpRequest), тож «обриву» насправді не було. Прогін виглядав би як «Retry працює». Це спіймала перевірка, що обрив справді спрацював. Друга спроба знайшла справжній баг (F-22).
- **Тести, які проходять не з тієї причини.** Тест, позначений «очікувано падає», лишається зеленим щоразу, коли падає, з будь-якої причини, навіть через помилку в підготовці даних. Тому я додав власний звіт, який показує точну перевірку, на якій падає кожен відомий баг.
- **Цифри, які не сходились.** AI написав підсумки тест-кейсів на око (75 перевірок, хоча було 68). Відтоді кожен підсумок у документах рахує скрипт, а кожен ID автотесту звіряється зі справжнім списком тестів.
- **Вигадані деталі.** В одному прикладі API AI написав id, якого ніколи не було в справжній відповіді. Я замінив його заглушкою: кожен запит і відповідь у звіті мають бути справжніми.
- **Лікування симптому, а не причини.** Прогін тестів іноді не завершувався. Перше «виправлення» (вимкнути trace-файли) лише сховало проблему. Справжня причина — Node 26, якого Playwright ще не підтримує. Тепер npm-скрипти автоматично запускаються на Node 22, і прогін завершується сам.
- **Чого AI не міг перевірити взагалі.** Справжній drag-and-drop з комп'ютера, людський подвійний клік і реєстрацію з чужим email із запрошення (F-21). Це я робив руками.
